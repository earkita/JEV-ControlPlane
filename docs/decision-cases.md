# Decision cases API

Use a stateless JSON document to send states and candidate decisions to the resident model. No cases or generated content are saved by the server. The existing `/v1/systemone` endpoint remains available when you already have its typed `questions` map; this format uses arrays and stable IDs, which are easier to generate and validate.

```text
Case batch
  cases[]
    id                 unique case ID
    state              text, JSON object, or JSON array
    provenance         optional string metadata about the generator or dataset
    questions[]
      id               unique within the case
      question         instruction to the decision model
      options[]        2–16 {id, description} candidates
      expected_option  optional option ID for evaluation
  scorer               optional: semif or likelihood
  temperature          optional positive number
  mode                 direct (default) or shared (Torch SemIf only)
```

Question IDs, option IDs, and case IDs must be unique in their respective scopes. `expected_option` must name one of the question's options. Extra fields are rejected, and a batch may contain at most 16 cases and 64 questions. Malformed input returns HTTP 422 with field-level errors. A prompt over the model's context limit fails clearly. The GGUF OpenJev 27B profile accepts SemIf direct; it rejects likelihood and shared mode.

The expected option is **never included in the model prompt**. It is compared to the returned choice after scoring. Unlabelled questions return `matched: null` and are excluded from the summary accuracy. A label generated by another AI model is a proposed answer, not verified ground truth; review labels before treating the summary as an accuracy measure.

Start from [decision-cases.json](../examples/decision-cases.json). Against the running 27B profile:

For a browser workflow, open `http://127.0.0.1:8002/ui`, keep the default **Wklej JSON** tab, paste the batch and select **Oceń JSON**. The panel groups decisions by case, shows each option's probability and marks agreement with optional labels. You can also paste a single case object or an existing `/score` or `/v1/systemone` request. The JSON document supplies its own scorer, mode and temperature when needed; otherwise the server defaults apply.

```bash
curl -sS http://127.0.0.1:8002/v1/cases/validate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/decision-cases.json

curl -sS http://127.0.0.1:8002/v1/cases/evaluate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/decision-cases.json
```

The first endpoint checks shape and IDs without scoring. The second returns each model choice, probability distribution, confidence, prompt hash, model revision, timing, `matched` value and an aggregate summary. It evaluates all questions in a case against the same state. If `OPENJEV_API_KEY` is set, pass `-H "Authorization: Bearer $OPENJEV_API_KEY"` to both requests.

The Python HTTP client and CLI expose the same operations:

```bash
openjev-semif client cases-validate --url http://127.0.0.1:8002 --input examples/decision-cases.json
openjev-semif client cases-evaluate --url http://127.0.0.1:8002 --input examples/decision-cases.json
```

```python
import json
from openjev_semif import OpenJEVClient

with open("examples/decision-cases.json") as file:
    batch = json.load(file)
with OpenJEVClient("http://127.0.0.1:8002", timeout=120) as client:
    client.validate_cases(batch)
    result = client.evaluate_cases(batch)
    print(result.cases[0].questions[0].answer.choice)
```

To generate fixtures with another AI model, ask it for **JSON only** in the shape of [decision-cases.json](../examples/decision-cases.json). Give it the allowed option IDs and require `expected_option` to be one of those IDs. Put the generator name and dataset/version in `provenance`. Validate the generated JSON first, then review the expected answers, and finally evaluate it. The decision service does not call a generator model; generation stays independent of inference and scoring.
